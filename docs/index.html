Contar la bodega sin contar la bodega

Una app móvil (iOS y Android) que lee el código de barras del producto, registra su entrada o su salida y avisa cuando queda poco. Todo en el teléfono, sin servidor y sin conexión.

El problema

El cuaderno no sabe cuántos quedan

En una bodega de ejemplo (caso hipotético) el stock se controla a ojo. Dos cosas fallan siempre: un producto se agota sin que nadie lo note hasta que un cliente lo pide, y otro se compra de más porque quedaban cajas atrás.

Lo que pasa hoy

Alguien recorre la estantería, cuenta a ojo y anota en un cuaderno. El número envejece el mismo día.

Lo que ya existe

Cada producto trae impreso un identificador único, y cada teléfono trae un lector capaz de leerlo. Falta unirlos.

Lo que construimos

Escanear, registrar el movimiento y ver el stock al instante. Sin escribir el código, sin contar la estantería.

El dato que cambia la decisión del dueño no es el inventario de ayer: es cuántas unidades hay ahora.

Alcance

Lo que hace y lo que deliberadamente no hace

Dentro del alcance
  • Escaneo del código de barras con la cámara
  • Alta de un producto nuevo cuando el código no existe
  • Movimientos de entrada y de salida
  • Alerta visual cuando el stock llega al mínimo
  • Búsqueda, filtro de stock bajo e historial
  • Ingreso manual del código como ruta alternativa
Fuera del alcance, y por qué
  • Sincronización entre teléfonos. Necesita servidor, cuentas y resolución de conflictos sin conexión. Hacerlo a medias pierde datos en silencio.
  • Ventas contables y proveedores. Se guarda precio unitario CLP y valorización de movimientos, pero no se implementa facturación.
  • Quién hizo cada movimiento. Ese campo convertiría la bitácora en un registro de actividad de trabajadores identificables.

Una limitación reconocida suma. Una limitación escondida se nota.

Arquitectura

Cuatro capas y una regla verificable

La regla, comprobable

Ningún archivo de src/screens ni de src/components contiene SELECT, INSERT ni UPDATE.

Lo que eso compra

Las consultas del inventario se concentran en src/db. Sustituir SQLite también exige adaptar el proveedor, el esquema y la medición.

Y además

gtin.ts y stock.ts no importan React ni Expo y se prueban con Node sin levantar la app. Esto permite verificar las reglas de forma independiente.

Permisos

Un permiso rechazado no puede romper la app

La pantalla propia explica el uso de la cámara antes del diálogo del sistema. El permiso se solicita cuando el usuario decide continuar con la lectura.

El quinto estado

permission vale null mientras el sistema lo consulta. Tratar ese nulo como "denegado" hace parpadear la explicación cada vez que se abre el escáner.

Lo que pedimos

Solo cámara. Sin micrófono: recordAudioAndroid: false en app.json.

La prueba

Si el usuario dice que no, escribe los dígitos impresos bajo las barras y trabaja igual.

El escáner

Tres detalles que no se ven y deciden si sirve

1 · El candado

onBarcodeScanned se dispara varias veces por segundo sobre el mismo código. Sin candado, un escaneo abre la ficha una docena de veces.

useRef bloquea tras la primera lectura y se libera al volver a la cámara.

2 · La cámara apagada

La documentación advierte que solo puede haber una vista previa activa y que hay que desmontarla al perder el foco.

Escuchamos AppState y limpiamos la suscripción en el retorno del efecto. Olvidar esa limpieza no da error: solo gasta batería.

3 · Los tipos

Aceptar los trece tipos que soporta la biblioteca multiplica las lecturas falsas sobre etiquetas de precio y códigos QR de publicidad.

Restringimos a tres. Dejamos fuera code128, que es alfanumérico y de largo libre: nunca pasaría la validación del dígito verificador, así que el usuario solo vería "lectura incompleta".

Validación

El dígito verificador filtra la basura

Una etiqueta arrugada o con poca luz produce lecturas corruptas. Validar en memoria evita una consulta a la base por cada lectura basura.

// src/lib/gtin.ts · algoritmo módulo 10 de GS1
export function calcularDigitoVerificador(cuerpo) {
  if (!/^\d+$/.test(cuerpo)) return null;
  // El peso depende de la posición DESDE LA DERECHA:
  // por eso se invierte antes de recorrer.
  const suma = cuerpo.split('').map(Number).reverse()
    .reduce((acc, n, i) => acc + n * (i % 2 === 0 ? 3 : 1), 0);
  return (10 - (suma % 10)) % 10;
}

Y de paso, sin duplicados

Un UPC-A de 12 dígitos se normaliza a 13 con un cero adelante. El mismo producto no queda cargado dos veces según el simbolismo que se haya leído.

Persistencia

Dos tablas y una transacción

-- esquema resumido; el completo está en el Código 2 del informe
CREATE TABLE productos (
  codigo  TEXT    PRIMARY KEY,
  nombre  TEXT    NOT NULL,
  stock   INTEGER NOT NULL CHECK (stock >= 0),
  minimo  INTEGER NOT NULL DEFAULT 5
);

CREATE TABLE movimientos (
  id       INTEGER PRIMARY KEY AUTOINCREMENT,
  codigo   TEXT    REFERENCES productos(codigo),
  tipo     TEXT    CHECK (tipo IN ('IN','OUT')),
  cantidad INTEGER CHECK (cantidad > 0),
  fecha    INTEGER NOT NULL
);
Por qué guardar el stock si existe la bitácora

Calcularlo con SUM() es correcto el primer día y cada vez más lento, porque la bitácora puede crecer. Leer la columna evita agregar todos los movimientos en cada consulta; su duración debe medirse.

Y cómo evitamos que se desincronicen

Leer el stock, actualizarlo e insertar el movimiento van en una sola transacción exclusiva. Sin ella, dos escaneos rápidos leen el mismo stock y se pisan.

La última línea de defensa

CHECK (stock >= 0). Si la interfaz falla, el motor rechaza la escritura.

Inyección SQL

Todas las consultas van parametrizadas. execAsync no escapa valores, así que nunca recibe texto escrito por el usuario.

El código que no existe no es un error

Abre la pantalla de alta con el código ya cargado y bloqueado, y pide nombre, stock inicial y mínimo. Lo que para el usuario sería un error pasa a ser el camino normal para recibir una caja nueva.

El vacío que todos olvidan

Una lista sin productos que se ve igual que una lista que no cargó confunde por completo. Son pantallas distintas, con texto distinto.

Medición M1

Cómo medir la decisión

Buscar un producto por código entre 5.000, 30 veces por motor, con un código distinto cada vez. Pendiente de ejecutar y registrar en un teléfono físico. No se adjunta evidencia de dispositivo en este repositorio.

Condiciones de la medición

Equipo físico: iPhone [modelo], iOS [versión], Expo Go (SDK 58), tras [N] min de uso continuo. M2 y M3 medidos con performance.now() dentro de la app.

Por qué da esa diferencia

AsyncStorage guarda pares de clave y valor y no tiene índices: buscar obliga a leer la cadena completa, parsear el JSON y recorrer el arreglo. SQLite resuelve por clave primaria con un recorrido de árbol B.

Por qué importa

Ese camino se recorre en cada escaneo. Quien recibe un pedido escanea cuarenta cajas seguidas, y la espera se multiplica por cuarenta.

Transparencia metodológica

El emulador Android solo se usa para validar layout y BackHandler, nunca para tiempos. En iPhone bajo Expo Go ambos motores comparten el mismo hardware y entorno, pero el modo desarrollo puede alterar los tiempos. Registrar el entorno y repetir en release.

Cierre

Lo que aprendimos construyéndola

1 · El escáner casi no es la cámara

Leer el código es una llamada a la biblioteca. El tiempo se fue en el candado, la validación y decidir qué pasa cuando el código no existe. Esa última pregunta cambió el diseño.

2 · El permiso no es un trámite

Explicación previa, rechazo recuperable, rechazo definitivo con salida a Ajustes y ruta alternativa ocuparon más código que la pantalla de la cámara.

3 · Medir cambia el argumento

SQLite sobre AsyncStorage se podía defender con teoría. La medición pendiente permitirá contrastar esa decisión con resultados propios en el teléfono.

Lo que queda abierto

La sincronización entre dispositivos, que el local va a pedir apenas tenga dos personas moviendo stock a la vez. Resolverla bien significa decidir qué pasa cuando dos teléfonos sin conexión modifican el mismo producto, y esa pregunta es de arquitectura distribuida más que de desarrollo móvil.
